01 / CONTEXT

El desafío central fue convertir reglas operativas ambiguas en comportamiento de producto verificable.

DOMAIN

Reservas con modalidades distintas

El sistema diferencia ocio compartido, ocio exclusivo y eventos con ventanas horarias, disponibilidad y políticas propias.

CONSISTENCY

Concurrencia y holds

La disponibilidad y el precio son autoridad del servidor. Locks, holds y expiración evitan reservas incompatibles o estados inconsistentes durante el pago.

OPERATIONS

Administración trazable

El panel administrativo incluye consultas, cancelaciones, reprogramación, pricing, disponibilidad, confirmación de efectivo y un audit trail append-only.

03 / ENGINEERING DECISIONS

Reglas de negocio convertidas en invariantes del sistema.

01

Pricing autoritativo y snapshot histórico

El cliente no decide el precio. La API calcula y conserva el valor aplicado en la reserva para que cambios futuros de configuración no reescriban el pasado.

server authorityhistorical snapshot
02

Holds y expiración alrededor del pago

Una reserva pendiente puede bloquear disponibilidad por una ventana controlada. El diseño trata la expiración como parte del dominio, no como una corrección manual posterior.

advisory locksholdsexpiration
03

Mercado Pago y efectivo con responsabilidades distintas

Los pagos online siguen el flujo del proveedor; el efectivo requiere confirmación administrativa. La UI no simula confirmaciones que pertenecen al backend o a un operador.

Mercado Pagocash confirmationRBAC
04

Documentación como parte del producto

Visión, alcance, requisitos, reglas, decisiones, arquitectura, seguridad, DevOps y FinOps viven versionados junto al código para que las decisiones sean rastreables.
